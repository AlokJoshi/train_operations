A factory function like createStation(name, x, y, dwellTicks) has these advantages over new Station(...):

No new keyword required

Calling createStation(...) is just a function call — no risk of forgetting new and silently getting undefined or corrupting the global scope.
Flexible return type

The factory can decide what to return — a plain object, a class instance, a frozen object, or even a different subtype based on input (e.g., a terminus station vs. a passing station), without changing the call site.
Easier to compose and test

A plain object returned from a factory has no prototype chain to worry about. Mocking in tests is trivial — just pass in a literal { name, x, y, dwellTicks }.
Encapsulation without classes

You can close over private state using variables in the factory's scope, without needing #privateField syntax.
Consistent with how your codebase works

Your existing objects (Flyover, Intersection) are constructed with new, but station data is essentially a value object — it holds data, not behavior. A factory returning a plain object is idiomatic for that.
Practical example in your context:


// Factory — returns a plain data objectfunction createStation(name, x, y, dwellTicks, stopOnReturn = true) {  return { name, x, y, dwellTicks, stopOnReturn, distanceFromStart: null }}// vs class — adds prototype overhead for a pure data recordclass Station {  constructor(name, x, y, dwellTicks, stopOnReturn = true) { ... }}
For a station, which is just a data record attached to a route, the factory is the right choice — it produces plain, serializable objects with no overhead.

laneOccupancy is the runtime map that tracks which train is currently occupying each grid cell, per lane.

How it is structured:
1. It is initialized as a Map in `Intersections.js:12`.
2. Top-level key is a cell key string from row,col via `Intersections.js:16`.
3. Value is another Map for lanes at that cell:
- lane number -> train number

So conceptually:
- cell 10,20 -> { lane 0: train 2, lane 1: train 5 }

How it is used in updateIntersection:
1. Cell bounds and special-cell guard run first in `Intersections.js:106`.
2. It fetches per-cell lane map:
- occupancyByLane = laneOccupancy.get(cellKey) at `Intersections.js:116`
3. If trainNumber is null/undefined, it means clear occupancy for that lane:
- delete lane entry
- remove cell entry if no lanes remain
- this is in `Intersections.js:118-126`
4. If a train is entering:
- it checks current train on same lane
- if same lane already has a different train, collision logic runs
- if allowedTrainsByCell says both are allowed at that cell, collision is skipped
- collision branch is in `Intersections.js:130-152`
5. If no conflict:
- it sets lane -> train in the per-cell map
- stores map back to laneOccupancy
- in `Intersections.js:153-155`

Why per-lane matters:
1. Two trains can be in same cell without collision if they are on different lanes (depends on how caller passes lane).
2. Collision check is lane-specific, not just cell-specific.

When it gets cleared:
1. Flyover/station update clears occupancy for that cell in:
- `Intersections.js:163`
- `Intersections.js:171`
2. removeTrain walks all laneOccupancy entries and removes that train from every lane in `Intersections.js:175-187`.

In short:
- laneOccupancy is the live occupancy state used for immediate collision detection.
- intersections grid stores static cell type state like Flyover/Station.
- laneOccupancy is dynamic, updated every movement step.
